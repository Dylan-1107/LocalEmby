# 立项调研报告：移动端全量用户数据读取能力（通讯录 / 短信 / 相册 / 文件）

> 版本：v1.0（立项调研阶段，未涉及任何代码改动）
> 日期：2026-10-21
> 结论先行：**"直接读取手机上全部数据"在 iOS 上不可行，在 Android 上可行但属于高限制权限，全平台合规风险极高**。建议按"最小必要 + 系统选择器优先"的架构立项，而非申请全量宽权限。

---

## 一、调研背景与目标

目标：评估让应用实现"直接读取手机上的全部数据"（通讯录、短信、相册、文件等）的技术可行性，覆盖 Android / iOS 两大平台的权限机制、系统限制、可行技术方案、用户授权方式，并给出难度评估与后续阶段规划。

**重要前提说明**：本报告区分两个概念——
- **全量读取**：应用在后台枚举并读取设备上所有通讯录 / 短信 / 相册 / 文件；
- **按需访问**：用户在使用某个功能时，通过系统选择器（Picker）主动挑选具体数据交给应用。

现代移动 OS 的设计方向是**把前者逐步封死、把后者做成标准体验**。立项时必须先明确业务需要的是哪一种。

## 二、Android 平台现状

### 2.1 权限机制总览

Android 采用"清单声明 + 运行时授权"模型，敏感权限分为：

| 类别 | 说明 | 典型权限 |
|---|---|---|
| Normal | 安装即授予 | INTERNET 等 |
| Dangerous | 运行时弹窗授权，用户可拒绝/随时撤销 | READ_CONTACTS、READ_MEDIA_IMAGES |
| Restricted（受限） | 除运行时授权外，还需向应用商店提交声明表审核 | READ_SMS、READ_CALL_LOG、READ_MEDIA_IMAGES/VIDEO（Play 政策层面） |
| Special | 需引导用户到系统设置页开启 | MANAGE_EXTERNAL_STORAGE（所有文件访问） |

### 2.2 分数据类型详解

#### ① 通讯录（READ_CONTACTS）
- **机制**：Dangerous 权限，运行时弹窗，用户可拒绝或随时在设置中撤销。
- **系统限制**：可通过 ContactsContract API 全量枚举。
- **商店政策（重大变化）**：Google Play 已宣布新政策——**targetSdk 37+（Android 17 世代）起，仅当 Android Contact Picker 不足以支撑核心功能时才允许申请 READ_CONTACTS**，且必须提交 Play Console 声明说明为何 Picker 不够。政策方向：用一次性联系人选择器替代全量通讯录读取。
- **替代方案**：`ACTION_PICK` / Contact Picker API，用户逐个（或多选）挑选联系人，无需任何权限。

#### ② 短信（READ_SMS 等）
- **机制**：**Android 系统层面就要求应用必须先被用户设置为"默认短信应用"**，否则即使声明 READ_SMS 也拿不到数据。
- **商店政策（最严格的一类）**：Google Play 明确规定——不具备默认短信/电话/助理处理程序能力的应用，**连在 Manifest 中声明 SMS 权限组都不允许（包括占位文本）**；必须提交声明表，用途仅限已公示的核心功能，禁止用于广告/分析，禁止用其他 API 绕过。
- **国内现状**：国产 ROM（MIUI/HarmonyOS/ColorOS 等）对短信读取有额外管控，且短信验证码场景官方推荐使用 SMS Retriever API。
- **结论**：短信全量读取 = 必须做成"短信管理类"应用才有生存空间，对绝大多数产品是**死路**。

#### ③ 相册 / 媒体（演进最快的领域）
- **Android 12 及以下**：READ_EXTERNAL_STORAGE。
- **Android 13**：拆分为 READ_MEDIA_IMAGES / READ_MEDIA_VIDEO / READ_MEDIA_AUDIO，运行时授权。
- **Android 14**：引入 **Selected Photos Access（部分照片访问）**——用户可选择只授权部分照片，新增 READ_MEDIA_VISUAL_USER_SELECTED 权限；应用必须实现"全量 / 部分 / 拒绝"三态 UI 和重新选择流程。
- **Android 15/16**：进一步强化 Photo Picker（无需任何存储权限）、支持 QUERY_ARG_LATEST_SELECTION_ONLY 等；平台方向明确：**Picker 是标准，宽权限是例外**。
- **替代方案**：
  - **Photo Picker**（推荐）：零权限、系统级 UI、跨版本一致体验；
  - 自建相册选择器：需存储权限 + Play 声明表 + 三态处理，维护成本高。

#### ④ 文件（全文件系统）
- **Scoped Storage（Android 10+）**：应用默认只能访问自身私有目录和媒体集合，不能随意浏览整个文件系统。
- **MANAGE_EXTERNAL_STORAGE（所有文件访问）**：Special 权限，需引导用户到设置页手动开启；**Google Play 对此权限白名单审核极严**（文件管理器、杀毒等少数品类可过），一般应用直接拒绝。
- **标准替代**：SAF（Storage Access Framework）/ Documents Provider——用户通过系统文件选择器挑选文件或授权整个目录（ACTION_OPEN_DOCUMENT_TREE），应用获得对应 Uri 的持久化读写授权，无需存储权限。
- **国产 ROM 差异**：各厂商对后台读文件、外部存储路径有额外限制，需逐机型适配。

### 2.3 Android 小结

| 数据 | 全量读取可行性 | 用户授权方式 | 推荐方案 |
|---|---|---|---|
| 通讯录 | 可行（政策收紧中） | 运行时弹窗 | Contact Picker 优先，宽权限需声明 |
| 短信 | 极难（须为默认短信应用） | 设默认应用 + 运行时 | 基本不可行，验证码走 Retriever |
| 相册 | 可行但三态化 | 运行时弹窗 + 部分授权 | Photo Picker 优先 |
| 文件 | 全盘须白名单特殊权限 | 系统设置页手动开启 | SAF / Document Picker |

## 三、iOS 平台现状

### 3.1 核心机制：沙盒 + Entitlements + TCC

- **App Sandbox**：每个应用有内核级强制的独立容器（Container），**无法访问其他应用的数据和系统分区（只读挂载）**，这不是策略而是内核硬墙。
- **Entitlements**：能力钥匙，须在签名时声明，缺失即被系统拦截。
- **TCC（Transparency, Consent and Control）**：访问敏感数据的弹窗授权框架，用户可随时在"设置 → 隐私与安全性"中撤销。

### 3.2 分数据类型详解

| 数据 | 能否读取 | 方式与限制 |
|---|---|---|
| 通讯录 | **可以** | Contacts 框架，运行时弹窗（CNContactStore），用户可拒绝/撤销；可全量枚举 |
| 短信 | **完全不可行** | iOS **不向第三方应用提供任何短信读取 API**（验证码场景可用系统自动填充），无任何变通，越狱除外 |
| 相册 | **可以但分级** | iOS 14 起三档：全部照片 / 仅选中的照片 / 不允许；PHPickerViewController 无需授权即可选图；Limited Library Access 需支持重新选择流程 |
| 文件 | **仅限系统选择器** | 无全局存储权限概念；只能通过 UIDocumentPickerViewController 临时获取用户主动选取的文件；"文件"App 仅暴露应用自己声明的目录 |
| 其他应用数据 | **不可行** | 沙盒硬隔离，仅 App Group（同一开发团队）内共享 |

### 3.3 iOS 小结

- iOS 上"读取全部数据"**只能覆盖通讯录 + 相册（用户允许全量时）+ 用户手动选取的文件**；
- 短信与其他应用数据**在任何授权方式下都拿不到**；
- 越狱设备不属于合规立项考虑范围。

## 四、隐私合规要求（重点风险项）

### 4.1 中国大陆法规

| 依据 | 对本项目的要求 |
|---|---|
| 《个人信息保护法》 | 告知—同意原则；**最小必要原则**（限于实现处理目的的最小范围）；处理**敏感个人信息**（通讯录、行踪轨迹等）须取得**单独同意** + 事前个人信息保护影响评估（PIPIA）；不得以用户不同意为由拒绝提供基本服务；用户有权撤回同意并要求删除 |
| 《App 违法违规收集使用个人信息行为认定方法》（2019 四部门） | 明确 6 大类 31 种违规情形：未公开收集规则、未明示目的方式范围、未经同意收集、**违反必要原则**（无相关功能却调用位置/媒体文件/通讯录/设备等非必要权限即属违规）、批量收集与服务无关信息等 |
| 《常见类型移动互联网应用程序必要个人信息范围规定》（2021） | 明确 39 类 App 的"必要个人信息范围"，超出范围收集即违规 |
| **2025 年四部门个人信息保护系列专项行动** | 正在重点治理"**无相关功能或未使用相关功能时调用位置、媒体文件、通讯录、设备等非必要权限**"的 App 与 SDK，分批次公开通报、限期整改、下架 |
| 《数据安全法》《网络安全法》 | 数据分类分级、本地化存储、安全保护义务 |

**国内合规底线**：申请的每一项权限都必须能对应到一个具体、已在隐私政策中披露、且真实存在的功能；"先要权限再说"的模式在当前监管环境下**必然被通报**。

### 4.2 海外应用商店政策

- **Google Play**：SMS / Call Log 为最高限制级（须为默认处理器 + 声明表）；照片/视频/通讯录宽权限自 targetSdk 33/37 起均需声明表并证明 Picker 不足；QUERY_ALL_PACKAGES、个人贷款类 App 直接禁用相关权限。
- **App Store**：隐私 nutrition labels 如实申报；敏感框架（如通讯录）用途说明字符串必填；过度收集会被审核拒绝或事后下架。

### 4.3 技术侧合规措施建议

1. 权限**按需增量申请**（contextual request），在功能触发时申请，不在启动时一揽子索权；
2. 隐私政策中逐项列明权限对应功能、数据类型、存储期限、是否出境；
3. 敏感信息（通讯录、短信）**尽量不落盘、不上传**，优先端内处理；
4. 提供权限拒绝后的降级路径（如手动输入）；
5. 上线前完成 PIPIA 评估与三方安全审计。

## 五、技术路径对比与难度评估

### 方案 A：全量宽权限读取（原生 API 全量枚举）
- **范围**：Android 全部（短信除外）、iOS 通讯录+相册全量。
- **优点**：功能上限最高，可做备份/同步/整理类深度功能。
- **缺点**：政策风险最高（Play 声明审核 + 国内专项行动重点打击对象）；Android 14+ 需实现全/部分/拒绝三态 + 重选流程；用户授权意愿低。
- **难度**：★★★☆（Android）／★★★★（iOS 合规过审难）
- **结论**：**不建议作为默认路径**，仅在有明确正当核心功能（如通讯录备份恢复工具）时申请，且只申请必需的最小权限集。

### 方案 B：系统选择器优先（Picker-first）✅ 推荐
- **内容**：Photo Picker（零权限选图）、Contact Picker、SAF/Document Picker、iOS PHPicker + DocumentPicker。
- **优点**：零/低权限 → 无需商店声明表、国内合规风险最低、用户信任度高、跨版本行为一致。
- **缺点**：无法后台枚举全量数据；用户逐次选择有交互成本；Android Photo Picker 可多选但有数量体验上限。
- **难度**：★★（标准 API，成熟方案）
- **结论**：**80% 的场景应走这条路**。

### 方案 C：混合架构（推荐立项形态）
- 常规功能全部走方案 B；对确有必要的 1–2 个深度功能（如"全量通讯录备份"）单独申请宽权限，配合单独同意弹窗、声明表、PIPIA。
- **难度**：★★★
- **结论**：风险与能力的最佳平衡点。

### 方案 D：非常规手段（无障碍服务、root/越狱、私有 API）
- **明确否决**：无障碍服务读取数据已被 Google Play/国内监管定性为违规且被重点治理；root/越狱破坏系统安全不可商用；iOS 私有 API 必被拒审。**立项报告不将其列为可选路径。**

## 六、建议的后续开发阶段规划

### Phase 0：需求收窄与合规前置（1–2 周）
- 逐条列出"到底要用通讯录/短信/相册/文件做什么"，映射为功能清单；
- 每项功能判定：Picker 能否满足？宽权限是否有不可替代性？
- 产出《权限-功能映射表》与《个人信息保护影响评估（PIPIA）初稿》。
- **里程碑：砍掉所有"Picker 已够用但仍想拿宽权限"的需求。**

### Phase 1：MVP（Picker-first）（2–4 周）
- Android：Photo Picker + Contact Picker + SAF 文件选择；
- iOS：PHPicker + Contacts 框架 + DocumentPicker；
- 权限申请全部上下文化（功能触发时申请）、拒绝后降级路径；
- 产出：可运行 Demo + 权限申请文案 + 隐私政策草案。
- **里程碑：零宽权限完成核心数据选取链路。**

### Phase 2：深度功能与受限权限（4–6 周，视 Phase 0 结论）
- 仅对确认必要的宽权限（如通讯录全量备份）实现：
  - Android：运行时授权 + 三态处理（全量/部分/拒绝）+ Play 声明表；
  - iOS：相册 Limited 模式重选流程、通讯录单独同意；
- 敏感数据端内处理，不落盘不上传（或加密 + 本地存储）。
- **里程碑：宽权限最小集通过商店审核预检。**

### Phase 3：合规加固与多机型适配（3–4 周）
- 国产 ROM（MIUI/HyperOS、HarmonyOS、ColorOS、OriginOS）权限行为矩阵测试；
- 权限撤销的运行时监听与数据清理；
- 完成隐私政策终稿、投诉/注销/删除通道、内部数据审计机制。
- **里程碑：通过自查清单（对照《认定方法》31 种情形逐项排除）。**

### Phase 4：上线与持续合规
- 商店提交（Play 声明表 + App Store 审核材料 + 国内备案/检测）；
- 监管通报跟踪、季度权限使用审计；
- 建立权限变更响应流程（OS 大版本更新时复查，如 targetSdk 37 通讯录新政）。

**总体排期估算：约 3–4 个月至可上线状态。**

## 七、结论与立项建议

1. **"直接读取全部数据"应修正为"在系统与法规允许范围内的最大化数据访问能力"**：
   - iOS：短信与其他应用数据物理不可行；相册可全量（用户授权）但必须支持 Limited 模式；
   - Android：短信须为默认应用（基本不可行）；相册/通讯录可行但政策持续收紧；全盘文件需白名单特殊权限。
2. **推荐按方案 C（混合架构）立项**：Picker-first 为主体 + 必要最小宽权限，配套完整合规工程。
3. **最大风险不在技术而在合规**：2025 年起四部门专项行动把"未使用功能时调用媒体文件/通讯录等非必要权限"列为治理重点，任何超出功能需要的权限申请都可能被通报下架。
4. **立项先决条件**：Phase 0 完成前不启动任何权限相关编码；权限-功能映射表须经过合规评审签字确认。
