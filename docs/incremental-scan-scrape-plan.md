# 识别与刮削增量化改造方案

> 项目：Embylite · 阶段：仅方案设计，未改动代码
> 日期：2026-10-21 · 前置：`docs/scraping-research-proposal.md`（刮削立项）已落地 v2.7.0
> 核心诉求：**媒体库变大后，重新扫描 / 重新识别 / 重新刮削不能再"每次从零开始"**

---

## 1. 现状诊断：为什么现在"每次都重新开始"

逐层看完代码后，"重"的成本分布在四个层面，且**强制全量按钮是最大的浪费源**。

### 1.1 扫描层（VideoLibrary）—— 进程一次全白扫

| 问题 | 位置 | 影响 |
|---|---|---|
| 扫描结果只有内存缓存（`volatile cache`） | `VideoLibrary.java:32` | 进程重启 / 点「刷新」(`invalidate()`) 后**全量重扫**，全盘模式遍历 `/storage/emulated/0` 深度 8 |
| 每个文件 `probeDuration()`（`MediaMetadataRetriever.setDataSource`） | `VideoLibrary.java:301` | 每个新文件几十~几百 ms；500 个文件仅探测时长就 30s+，且结果**不持久化**，下次再探一遍 |
| 全盘 `walkDeep` 与目录 `walk` 行为不一致 | `walkDeep` 传 duration=0 | 全盘扫描出的条目无时长，首次播放详情才补；目录扫描却全量探测 |
| 删除的文件无清理 | 全文件 | 文件删了，弹幕绑定/刮削状态永久残留，统计数字虚高 |

### 1.2 弹幕识别层（EpisodeMatcher）—— "重新识别"= 全员重做

- 「重新识别」按钮传 `force=true`（`VideoInfoPage.kt:170`）→ **所有**文件重新 POST `/api/v2/match`、重新下载海报，包括已绑定的 300 集。
- 正常扫描（force=false）时已绑定可跳过，但 `unmatched / needs_confirmation` 只有 5 分钟节流（`EpisodeMatcher.java:73`），**每次扫描过期后都重新请求弹幕源**——未命中的文件永远反复消耗网络。

### 1.3 刮削层（VideoInfoService）—— 最重的一层，浪费最夸张

| 问题 | 位置 | 量级估算（一部 30 集的剧） |
|---|---|---|
| 「重新刮削」`force=true` 全量重做 | `VideoInfoPage.kt:202` | 30 × (search + detail + season + poster) ≈ **120 次请求**，300ms 限速 + 网络延迟 ≈ 3~5 分钟 |
| **每集独立执行 `TmdbClient.search(seriesName)`** | `resolve()` 逐条目调 search | 同一部剧 30 集 = 30 次一模一样的搜索请求；N 部剧线性放大 |
| `SEASON_CACHE` 只在内存、上限 64 条清空 | `VideoInfoService.java:31,468` | 进程重启即失效；大库一季多部剧时反复清空重拉 |
| `needs_confirmation / unmatched` 过 5 分钟节流后**每次扫描都重搜 TMDB** | `resolve()` 退避逻辑只护 5 分钟 | 待确认条目永远处于"每次开 App 重搜一遍"的状态 |
| 剧集海报每集重复下载、重复写 `poster.jpg` | `scrape()` + `writeNfo()` | 30 集同一张海报下载 30 次、写盘 30 次 |
| 确认一部剧候选后，同剧其他集仍各自待确认 | `confirm()` 只处理单条目 | 人工确认 30 集要点 30 次 |
| `running` 时新任务被静默丢弃，无取消 | `enqueue()` `if (running) return` | 扫描中点按钮无反馈；跑错批次只能等完 |

### 1.4 状态与身份层

- `item.id = 路径 CRC32`（`Item.java:77`）：**改名/移动文件 = 状态全丢**，绑定和刮削结果作废重做。
- 状态存 SharedPreferences 单键 JSON：千级条目可用，但无整体导出/迁移能力，且指纹里不含 mtime，改 `ScrapeTitle`/`EpisodeIdentity` 解析规则时无法让旧结果按需失效。

**小结**：指纹缓存骨架是好的（路径+大小+身份+数据源），缺的是三件事——
**① 扫描结果不持久化；② 缓存粒度停留在"文件级"，没有"剧集身份级"；③ 「重新识别/重新刮削」被设计成了全量重做。**

---

## 2. 设计目标与原则

| 目标 | 度量 |
|---|---|
| 进程重启后不重扫不重探 | 首页条目数秒出；时长/身份从索引直读 |
| 正常使用路径零重复网络请求 | 已成功条目永远不重发；待确认条目只在"有新理由"时重搜 |
| 「重新识别/刮削」默认增量 | 只处理 新增 + 失败重试 + 待确认；全量需显式确认 |
| 中断可续 | 任意时刻杀进程，下次从断点继续（状态已逐条落盘，天然支持） |
| 向后兼容 | 现有 `episode_bindings_v1` / `videoinfo_v1` 数据不迁移也能用，允许旧状态自然过期 |

## 3. 分层改造方案

### 第 1 层：媒体库索引持久化（VideoLibrary）

新增持久化索引 `library_index_v1`（JSON 文件存私有目录，或沿用 SP），每条记录：

```
path, size, mtime, durationMs, firstSeenAt
```

扫描流程改为 **walk（便宜）→ diff（内存比对）→ 增量动作**：

1. 目录遍历保留现状（`listFiles` 本身很快，不做更激进的 inotify/FS watcher，避免 ROM 兼容坑）；
2. 遍历结果与索引按 `path` 比对：
   - **新增**：`probeDuration()` 只探测这些文件 → 写索引 → 作为增量批次交给识别/刮削队列；
   - **变化**（size 或 mtime 不同）：更新索引、时长重探、指纹自然失效自动重刮；
   - **消失**：从索引移除 + 清理该 id 的弹幕绑定/刮削状态/播放进度外的海报引用；
   - **未变**：durationMs 直接从索引读，**不再 `setDataSource`**。
3. `get()` 命中索引时同步返回（不阻塞首页），后台线程静默 diff 后仅对增量入队；
4. 全盘扫描与目录扫描统一走同一套 diff，顺便修齐 `walkDeep` 不探时长的不一致。

> 收益：重启后"扫描"从 O(全库 × setDataSource) 降为 O(全库 × listFiles) + O(新增 × setDataSource)。

### 第 2 层：剧集身份级刮削聚合（VideoInfoService 核心重构）

引入**身份级缓存表** `series_meta_v1`，key 为归一化后的 `seriesName`（电影不参与，仍是文件级）：

```
key: normalizeTitle(seriesName) + "|" + 目录
value: tmdbId, show详情(NfoData), posterBytes引用, scrapedAt, fingerprint(解析规则版本号)
```

刮削主流程从"逐文件"改为"**按身份分组 → 逐身份 → 广播结果**"：

1. 入队时按 `seriesName` 分组：一部剧只执行 **1 次 search + 1 次 detail + 1 次海报下载**；
2. 分集只查 `(tmdbId, season)` 的分集信息——`SEASON_CACHE` 从内存升级为持久化（同 SP/JSON，含 fingerprint），去掉"超 64 条清空"；
3. `tvshow.nfo` 与剧集 `poster.jpg` 在身份级任务里**写一次**；分集 NFO 仍逐文件写（内容不同）；
4. `MetadataStore` 海报复用：同剧分集直接引用身份级海报 bytes，不再各自下载；
5. **确认继承**：`confirm()` 成功后，把 `(tmdbId, show)` 写入 `series_meta_v1`，同剧所有 `needs_confirmation` 集直接走 scrape 分支，不用逐个点确认；
6. 指纹增加**解析规则版本号**（如 `rules|3|`）：以后改 `ScrapeTitle`/`EpisodeIdentity` 规则时，改一个常量即可让旧结果精准失效，而不是全局瞎猜。

预期请求量（30 集剧）：全量 120 次 → **约 4 次**（search + detail + season + poster）。

### 第 3 层：队列治理与触发语义（两个 Service 通用）

**任务模式拆分**（`enqueue` 增加模式参数）：

| 模式 | 处理范围 | 触发点 |
|---|---|---|
| `INCREMENTAL`（默认） | 新增文件 + 指纹失效 + 失败到期重试 | 扫描后自动、首页「刷新」 |
| `RETRY` | 仅 failed / network_error / needs_confirmation | 待处理数 > 0 时按钮 |
| `FULL` | 全部条目（含已成功） | 「重新识别/重新刮削」改为**弹确认框**后才用 |

**待确认条目的重搜策略**：`needs_confirmation / unmatched` 不再靠 5 分钟节流硬扛，改为**显式状态**——只有以下情况才重搜：指纹变化、TMDB Key 变化、规则版本变化、用户手动重试、或数据源配置（弹幕源地址）变化。否则保持原状态安静躺着等人确认。

**退避升级**：失败重试从固定 15s/5min 改为指数退避（15s → 1min → 5min → 30min → 2h），状态里记 `attempts`，避免断网时无限空转。

**队列行为**：
- `running` 时新请求不再静默丢弃：同模式合并、不同模式排队并在 UI 提示"排队中"；
- 增加取消标志位，`progress` 字符串升级为结构化（已处理/总数/当前文件/可取消），视频信息页展示进度条；
- 两层（弹幕/刮削）队列互不阻塞保持现状，但共享同一个 `pace()` 限速预算，避免同时跑时把弱网打满。

### 第 4 层：状态迁移与存储升级（规模化后再做，M4 可延后）

- **软匹配迁移**：旧 id（路径 CRC）失配时，用 `sizeBytes + 解析身份(name/series/season/episode)` 在旧状态表里做二次查找，命中则继承状态——解决"改名/移动=全重做"；
- **存储**：条目接近千级时把两个 SP 合并迁移为单个 JSON 文件（便于导出调试），或 SQLite（若需要按状态筛选查询下推）。千级以内**不动**，SP 全量加载仍在毫秒级。

## 4. 触发点梳理（改造前后对照）

| 触发 | 现状 | 目标 |
|---|---|---|
| 启动服务器 / 首次 `get()` | 全量扫描 + 全量探测时长 + 全量入队 | 读索引秒出 → 后台 diff → 仅增量入队 |
| 首页「刷新」 | `invalidate()` 全量重扫 | 保留（= 强制 diff），但探测与入队仍增量 |
| 视频信息页「重新识别」 | force 全量重匹配 | 默认 RETRY；确认框选"全量重建"才 force |
| 视频信息页「重新刮削」 | force 全量重刮 | 同上 |
| 单条目确认候选 | 只处理当前条目 | 弹幕维持单条；刮削同剧继承（第 2 层） |
| 文件增删改 | 重启才感知，删除无清理 | diff 自动感知，增改入队、删清理 |
| TMDB Key / 弹幕源变更 | Key 变指纹失效（已有） | 保持 + 弹幕源地址也纳入弹幕指纹（已有）✓ |

## 5. 实施步骤

| 阶段 | 内容 | 交付物 | 备注 |
|---|---|---|---|
| M1 | 队列模式拆分（INCREMENTAL/RETRY/FULL）+ 待确认显式状态 + 指数退避 + 取消/排队 | 两个 Service 的 enqueue/resolve 改造 | **最小改动、收益最大**：先堵住"force 全量"和"待确认反复重搜"两个最大浪费 |
| M2 | 身份级刮削聚合：`series_meta_v1` + season 持久化缓存 + 确认继承 + 海报去重 | VideoInfoService 重构 | 请求量降 ~95%；纯逻辑部分可写成无设备回归（分组/继承策略） |
| M3 | 扫描索引持久化 + diff 增量 + 时长探测增量化 + 删除清理 | `LibraryIndex.java` + VideoLibrary 改造 | 顺带修齐 walkDeep/walk 不一致 |
| M4 | 软匹配状态迁移 + 存储升级 | 迁移工具逻辑 | 规模过千再做；不阻塞 M1–M3 |

依赖关系：M1 独立可先行；M2 依赖 M1 的模式拆分（增量批次按身份分组更自然）；M3 独立；M4 最后。

回归测试延续现有模式：分组策略、确认继承、退避表、索引 diff 都写成纯 Java 用例（`tests/` 下新增 `IncrementalRegression.java`），无需设备。

## 6. 风险与开放问题

1. **mtime 不可靠**：部分工具拷贝文件不保留 mtime → diff 用 `size + mtime` 双因子，仅 size 变才算变；mtime 变 size 不变视为可疑（大概率是 touch），跳过重探、只刷新记录。
2. **全盘 diff 仍要遍历目录树**：目录数量极大时 `listFiles` 也有成本，但相比 `setDataSource` 和网络请求低 2~3 个数量级，一期不做 inotify/watchService。
3. **SAF 条目的 mtime**：`DocumentsContract` 有 `COLUMN_LAST_MODIFIED`，可用；取不到时该条目退化为"每次都算未变"（按 size 兜底）。
4. **身份归一化规则变更**：`normalizeTitle` 改动会让 `series_meta_v1` 全体失配 → 已用"规则版本号指纹"兜底，失配即按新规则重建，代价可控（每个身份一次 search）。
5. **确认继承的误伤**：同目录同名剧的两个不同版本（如 1080p/4K 双份）会归入同一身份 → 身份 key 已含目录；若仍有错绑，继承只在"分集解析一致"时生效，歧义文件照旧不自动绑定。
6. **行为兼容**：老用户升级后首次启动，旧 SP 状态指纹不含规则版本 → 视为失配会重刮一遍，属一次性成本；可在指纹读取时对缺失版本号的旧记录视为"版本 0"并接受，避免首刷全量（推荐此做法）。

## 7. UI 交互与单条目纠错

### 7.1 三模式入口：默认动作 + 收起菜单

一个按键表达不了三种模式，改为"主按钮 = 默认安全动作，低频操作收进 ⋮ 菜单"：

- **三模式收敛为一行「识别范围 / 刮削范围」下拉（SuperDropdown）**：行尾显示当前选中值（默认"增量刷新"）+ ⌄；点击后在**行旁锚定弹出小浮层**（HyperLight「语言」选择同款 ListPopup 样式，非底部 sheet），三选项：增量刷新（当前项蓝色打勾）/ 重试失败与待确认 / 全量重建…（红色）；行下方摘要文案标注影响范围（如"2 个待确认 · 1 个失败"）
- **全量二次确认框**：写明范围（全部 N 个）、预计耗时、覆盖影响（已确认候选保留，已刮削结果覆盖），确认按钮红色
- 进度展示升级：进度条 + 当前文件 + 取消入口（配合 M1 队列治理的结构化 progress）

### 7.2 单条目纠错（刮错了只重刮一个）

"刮失败"和"刮错"是两回事：同一文件名重搜只会得到同样错的结果，force 重试救不了刮错。列表项展开详情后提供三个动作（只作用于该文件）：

| 动作 | 行为 | 网络成本 |
|---|---|---|
| **换一个** | 不重搜，列出上次搜索保存的 candidates 直接挑（`scraped` 状态也把 chosen + candidates 一并存入状态 JSON） | 零 |
| **重新搜索** | 弹窗预填解析出的关键词，**可手改**（换别名 / 外文名 / 加年份），新词搜索 → 候选列表 → 选中即刮 | 1 次 search + 详情 |
| **清除结果** | 清掉该条刮削状态回未刮削，恢复抽帧占位（本地 NFO 也错时用） | 零 |

配套状态语义：

- 人工选定后状态标记为 **`confirmed`（人工锁定）**：自动刮削永不覆盖，全量重建也跳过已锁定条目——人工意图 > 自动逻辑
- 人工锁定条目即使指纹失效（如规则升级）也不自动重刮，只降级为"提示人工复查"
- 与 M2 身份级继承的关系：**条目级人工选择优先于剧集级缓存**，被人工重选的分集脱离身份级自动结果，且其选择可反向写回 `series_meta_v1`（同剧其他集若还未刮，跟随人工选择）

### 7.3 实现映射（MiuiX 组件，HyperLight 同款风格）

用户指定采用 HyperLight（KiminonawaResa/HyperLight）设置页同款组件风格。Embylite 已依赖 miuix 0.8.8，所需组件全部现成（源码参考 `HyperLight-analysis/miuix-src/`）：

| 草稿元素 | MiuiX 组件 | 说明 |
|---|---|---|
| 分组小标题（"弹幕绑定"等） | `SmallTitle` | 替代现有 infoTab 区块标题 |
| 自动识别 / 自动刮削开关行 | `SuperSwitch` | 带图标 + 标题 + 摘要行 |
| **识别范围 / 刮削范围（三模式入口）** | `SuperDropdown` | **行旁锚定弹出 ListPopup**（HyperLight「语言」选择同款浮层，非底部 sheet）：增量刷新（当前项打勾）/ 重试失败与待确认 / 全量重建…（红色）；行尾显示当前选中值 + ⌄ |
| 绑定统计 / 状态行 | `SuperArrow` | 右侧 trailing 显示统计文字，点击进筛选列表 |
| 刮削进度条 + 取消 | `Slider`（禁用态）或 `ProgressIndicator` | 行内标题 + "21/35 · 取消" |
| 全量二次确认 / 重新搜索弹窗 | `SuperDialog` 风格自绘 | **实现注记**：SuperDropdown/SuperDialog 的弹层依赖 Miuix `Scaffold` 的 MiuixPopupHost，而本 App 是自绘结构未用该 Scaffold——故用 Compose `Popup`（锚定行尾）与全屏 overlay 按同款视觉自绘，外观与 HyperLight 一致、零宿主改造 |
| 单条目纠错（换一个/重搜/清除） | 详情展开区 + 重搜弹窗 | 见 §7.2 |

要点：

- 三模式不再做成三个按钮，收敛为**一行"识别/刮削范围"下拉**——默认值即增量刷新，语义与 §3 第 3 层的模式参数一一对应，选中即触发对应 enqueue
- `SuperDropdown` 弹层是 HyperLight 截图同款锚定样式（非底部 sheet），选中项蓝色打勾，危险项红色
- 设置页（tmdb key、自动刮削开关）可顺带迁移为同风格 `SuperSwitch`/`SuperArrow`，与视频信息页视觉统一

## 8. 结论

- 指纹缓存骨架不用推翻，**缺的是持久化索引、身份级聚合、任务语义拆分**三块；
- 优先级：M1（堵浪费）> M2（降请求量 95%）> M3（扫描提速）> M4（规模化再议）；
- 全部改动不引入新依赖，延续"纯 Java 核心 + 无设备回归测试"的既有模式。
